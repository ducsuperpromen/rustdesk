# Device Identity, Auto-Enrollment, and Unattended Access — Design

Phase 10 deliverable of the ENZU migration. This is a **design document, not an
implementation** — per the phase's own instruction ("do not implement portal yet"),
nothing in this document changes runtime behavior. It maps three future
capabilities onto extension points that already exist in the shared RustDesk core
(verified by reading `libs/hbb_common/src/config.rs` and `src/common.rs` at this
migration's baseline), so a future implementation phase has a concrete, low-risk
starting point instead of inventing new mechanisms from scratch.

No code in this repository was changed to produce this document. `src/enzu_config.rs`
and `build.rs` (the existing server-config injection) are unaffected and remain the
only mechanism actually wired up today.

## 1. Stable device identity

**Goal:** a per-device identifier that a future ENZU portal can trust as "this exact
device," independent of the user-facing, user-resettable RustDesk connect ID.

**What already exists and why it's the right anchor:**

- `Config::get_id()` (`libs/hbb_common/src/config.rs:1203`) is the human-facing
  rendezvous ID. It is explicitly designed to be user-changeable — `Config::update_id()`
  (`:1279`) regenerates it, and `Config::is_disable_change_id()` (`:1185`, backed by
  `BUILTIN_SETTINGS`) only optionally locks that down. **Not** stable enough to anchor
  device identity on: resetting it is a supported, expected user action.
- `Config::get_key_pair()` (`:1119`) generates an ed25519 keypair (`sign::gen_keypair()`)
  the *first* time it's needed, then persists it in the config store and caches it in a
  process-wide `KEY_PAIR` lock. It is **not** regenerated by an ID reset, has no exposed
  "reset keypair" UI action, and is already how RustDesk proves a device's identity
  cryptographically end-to-end. This is the natural stable-identity anchor: it already
  exists, is already generated exactly once per install, and changing nothing about it
  keeps this "preserve shared Rust core" — no new field, no new file.

**Design (for a future phase, not built now):** a device's stable identity would be the
SHA-256 fingerprint of the existing keypair's public key (`Config::get_existing_key_pair()`,
`:1148`, added specifically so a caller can check for an existing identity **without**
forcing generation of a new one as a side effect). A future `enzu_identity` module would:
1. Read the fingerprint via `get_existing_key_pair()` (never `get_key_pair()`, which
   would silently create an identity that hasn't gone through enrollment).
2. Expose it to Dart/Kotlin/Windows UI the same way `flutter_ffi.rs` already exposes
   other `Config` getters (e.g. `main_get_app_name_sync`, `src/flutter_ffi.rs:1097`),
   so an "ENZU Device ID" can be shown in Settings without any new native storage.
3. Never invent a second identity mechanism (e.g. a random UUID file) — one stable
   cryptographic identity, reusing what the core already maintains, is simpler and
   already trusted by the existing protocol.

## 2. Auto-enrollment API boundary (not implemented)

**Goal:** a fresh install should be able to register itself with an ENZU management
backend automatically, the same way `src/enzu_config.rs` already bakes in a default
server/key pair — except resolved at **first run** against a live portal instead of at
**build time** against `.env`/CI variables.

**Why this is additive to, not a replacement for, the existing config injection:**
`build.rs` -> `option_env!` -> `src/enzu_config.rs` -> `DEFAULT_SETTINGS` remains the
zero-network fallback (a device with no portal reachable, or built without one
configured, still gets the stock ENZU servers). Auto-enrollment would sit **above**
that path, not instead of it — see the settings-tier table below.

**Where it would hook in — the settings tiers `Config::get_option` and its policy
cousins already resolve, highest priority first:**

| Tier | Storage | Who can override it | Today's use |
|---|---|---|---|
| `OVERWRITE_SETTINGS` | in-memory | nothing (hard override) | admin push-configs already applied this run |
| `HARD_SETTINGS` / `BUILTIN_SETTINGS` | in-memory, set once at startup | not user-editable at all | `is_disable_change_id`, `is_incoming_only`, preset permanent-password storage (`get_preset_password_storage_and_salt`, `:1415`) |
| user-saved options | `CONFIG2.options`, persisted `RustDesk2.toml` | the user, in Settings | everything the user has explicitly changed |
| `DEFAULT_SETTINGS` | in-memory | anything above | **ENZU's current build-time injection** (`enzu_config.rs::apply_enzu_defaults`) |

An auto-enrollment client's natural boundary is therefore a new, small module
(sketched, not implemented, as `src/enzu_enrollment.rs`) with a single
responsibility: on first run, if a portal endpoint is configured (itself resolved the
same CI-env > `.env` > fallback way as today's server config — reusing `build.rs`'s
existing precedence code, not a new mechanism), call the portal once with the device's
stable identity (§1) and, on success, write the response into `HARD_SETTINGS`/
`BUILTIN_SETTINGS` (device is now managed: locked servers, locked ID, group/strategy
metadata) rather than `DEFAULT_SETTINGS` (which a local user could still override).
This mirrors a distinction RustDesk's own core already draws — `DEFAULT_SETTINGS` is
"suggested," `HARD_SETTINGS`/`BUILTIN_SETTINGS` is "enforced" — so enrollment outcomes
would naturally belong in the enforced tier, exactly where `is_disable_change_id` /
`no_register_device` / preset-password already live.

**API boundary sketch (design only — no such trait/module exists yet):**

```
trait EnrollmentClient {
    // Called once at first run if a portal endpoint is configured.
    // `device_fingerprint` is the stable identity from §1.
    fn enroll(&self, device_fingerprint: &str) -> Result<EnrollmentResult>;
}

struct EnrollmentResult {
    rendezvous_server: Option<String>,   // same shape as ENZU_ID_SERVER
    relay_server: Option<String>,        // same shape as ENZU_RELAY_SERVER
    public_key: Option<String>,          // same shape as ENZU_PUBLIC_KEY
    preset_permanent_password: Option<String>,   // -> HARD_SETTINGS (see §3)
    lock_id: bool,                       // -> BUILTIN_SETTINGS: disable-change-id
    device_group: Option<String>,        // -> reuses OPTION_PRESET_DEVICE_GROUP_NAME
}
```

Deliberately not decided here (a portal-design question, out of scope for this phase):
transport (HTTPS to what host, whether it's the same host as `ENZU_ID_SERVER`),
authentication of the enrollment call itself, retry/offline behavior, and revocation.
This section only establishes *where in the existing settings model* the result of
enrollment would land, so a later phase can implement the actual client without having
to first reverse-engineer the settings hierarchy.

## 3. Unattended access strategy (not implemented)

**Goal:** a managed (enrolled) device should be reachable without a human at the
keyboard approving each connection, without inventing a new password/auth mechanism.

**What already exists and why it's sufficient:** RustDesk already has exactly this
concept, gated by a **preset permanent password**, not a new feature:

- `Config::get_preset_password_storage_and_salt()` (`config.rs:1415`) reads
  `HARD_SETTINGS["password"]` / `["salt"]` — a permanent password that can be supplied
  *without* going through the interactive "set my own password" flow.
- `Config::set_permanent_password()` (`:1293`) already special-cases this: a user
  can't overwrite a preset password if `is_disable_change_permanent_password()`
  (`:1176`, also `BUILTIN_SETTINGS`-backed) is set — i.e. the enforced/managed tier
  already wins over the user tier for exactly this setting today.
- `Config::has_permanent_password()` (`:1394`) / `has_local_permanent_password()`
  (`:1440`) are what the connection-accept path checks to decide whether a session
  needs interactive approval at all — a device with a valid preset password is already
  "unattended-access-ready" by upstream's own definition, no ENZU-specific runtime
  change required.
- `Config::no_register_device()` (`:1167`, `OPTION_REGISTER_DEVICE`) and
  `OPTION_PRESET_DEVICE_GROUP_NAME` / `OPTION_PRESET_STRATEGY_NAME` (`:2946`, `:2978`,
  `:2980`) show RustDesk's own enterprise story already has a "device belongs to a
  managed group/strategy" concept at the option-key level, even though nothing in this
  fork populates it yet.

**Strategy (for a future phase):** auto-enrollment (§2) supplies
`preset_permanent_password` into `HARD_SETTINGS["password"]`/`["salt"]` and sets
`is_disable_change_permanent_password` — using the *existing* preset-password code path
end-to-end. No new password storage, no new auth handshake, no change to
`libs/hbb_common`'s crypto. The only new work in a later phase is the enrollment client
that populates these existing hard settings; the unattended-access behavior itself is
already implemented upstream and merely needs to be **fed**, not built.

**Explicitly deferred to a later phase, once the portal exists:** how an administrator
revokes unattended access remotely, how a preset password rotates, and whether
`is_incoming_only` / `no_register_device` should be part of the same enrollment payload.

## Relationship to earlier phases

- Does not touch `src/enzu_config.rs`, `build.rs`, or `scripts/verify_enzu_config.py` —
  the existing build-time config injection is unaffected and remains authoritative
  until an enrollment client (§2) is actually built.
- Does not touch `libs/hbb_common` (submodule) — every mechanism cited above already
  exists there today; this document only maps ENZU's future needs onto it.
- Consistent with [SOURCE_LAYOUT.md](SOURCE_LAYOUT.md)'s `config/` ownership: a future
  `src/enzu_enrollment.rs` would belong next to `src/enzu_config.rs`, documented from
  `config/README.md`, not physically moved anywhere.
