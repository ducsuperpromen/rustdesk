# RustDesk / ENZU Architecture

Verified against the checked-out source on branch `feature/enzu-custom-client`. Line
references are to files in this repository.

RustDesk is a Flutter UI on top of a Rust core, joined by flutter-rust-bridge. The same
Rust core provides both the "controlling" and "controlled" (server) roles.

## 1. Flutter layer (UI)

- `flutter/lib/**` — Dart application: screens, connection UI, settings.
- Talks to the Rust core exclusively through the generated bridge
  (`flutter/lib/generated_bridge.dart`, git-ignored, produced in CI).
- The network/ID-relay settings screen reads/writes the same options the Rust core
  resolves (`custom-rendezvous-server`, `relay-server`, `key`) — so an embedded
  default is transparently visible and overridable in the UI.

## 2. Rust core

- `src/**` — the RustDesk client core (crate builds `librustdesk`).
  - `src/core_main.rs` — desktop/native entry (`core_main()`); runs for every desktop
    process, including the Windows `--server` subprocess. Calls `load_custom_client()`
    then, for ENZU, `enzu_config::apply_enzu_defaults()` (`core_main.rs:35`).
  - `src/common.rs` — shared helpers: `get_key()` (`:1804`, key resolution),
    `get_rs_pk()` (`:2004`, public-key parsing/validation), `read_custom_client()`,
    `load_custom_client()`.
  - `src/rendezvous_mediator.rs` — connects to hbbs, registers the device ID, drives
    hole-punching / relay negotiation.
  - `src/client.rs` — outbound connection logic, key/relay usage (`RS_PUB_KEY` fallback
    at `:767`, `:1806`).
  - `src/server/**` — controlled-side (incoming connection) handling.
  - `src/custom_server.rs` — upstream exe-filename / signed custom-client parsing
    (not used by ENZU; see NETWORK_FLOW / CUSTOMIZATION_GUIDE).
  - **`src/enzu_config.rs` — ENZU source of truth (NEW).** Constants + `apply_enzu_defaults()`.
- `libs/hbb_common/src/config.rs` — configuration store and resolution (see §6).

## 3. Flutter ↔ Rust bridge

- `src/flutter_ffi.rs` — the FFI surface exposed to Dart. `initialize(app_dir,
  custom_client_config)` (`:40`) is the earliest Rust entry for Flutter apps
  (Android + Flutter desktop); ENZU calls `apply_enzu_defaults()` here too.
- `src/bridge_generated*.rs` / `flutter/lib/generated_bridge.dart` — generated by
  `flutter_rust_bridge_codegen` (git-ignored; produced in CI/builder image).

## 4. Android native / JNI layer

- `flutter/android/**` — Gradle project; `app/build.gradle` (signing, ABI), Kotlin.
- `flutter/android/app/src/main/kotlin/**/ffi.kt` — JNI glue that loads the native lib.
- `flutter/android/app/src/main/jniLibs/arm64-v8a/` — `librustdesk.so` (the Rust core)
  and `libc++_shared.so` are placed here during the build.
- On Android the controlling and controlled roles run **in one process**, so a single
  `apply_enzu_defaults()` at `initialize()` covers everything.

## 5. Windows layer

- `build.py` orchestrates the desktop build; the Flutter Windows runner embeds the
  Rust core.
- Windows spawns **multiple processes** (UI, `--server`, `--cm`). All pass through
  `core_main()`, which is why ENZU defaults are applied there — the `--server`
  process is the one that registers with hbbs.

## 6. Configuration resolution layer

`libs/hbb_common/src/config.rs` (upstream). Priority tiers, highest first:

1. `OVERWRITE_SETTINGS` (`:77`)
2. user-saved options — `CONFIG2.options` (persisted `RustDesk2.toml`)
3. `DEFAULT_SETTINGS` (`:76`) ← **where ENZU injects defaults**

`Config::get_option(k)` implements exactly this order (`:1245`). Effective servers:

- ID/rendezvous: `Config::get_rendezvous_server()` (`:913`) → `custom-rendezvous-server`
  option → … → `RENDEZVOUS_SERVERS` constant fallback (`rs-ny.rustdesk.com`, `:120`).
- relay: `relay-server` option (`OPTION_RELAY_SERVER`, `:2954`).
- key: `get_option("key")` → fallback `RS_PUB_KEY` constant (`:121`), via
  `common::get_key()`.

Because ENZU writes only `DEFAULT_SETTINGS` (in-memory), user/admin values always win
and nothing is persisted on startup.

## 7. Networking layer

- Client → **hbbs** (ID/rendezvous, `remote.enzutech.de:21116`) to register its ID and
  discover peers.
- Peer connection attempts **direct / NAT hole-punching** first.
- On failure, falls back to **hbbr** relay (`relay.enzutech.de:21117`).
- Server identity/encryption uses the embedded **public key**; RustDesk's end-to-end
  encryption and key verification are unchanged (ENZU only selects which server + key).

See `NETWORK_FLOW.md` for the full sequence and `BUILD_FLOW.md` for how the binaries are
produced.
